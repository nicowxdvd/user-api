== Bloqueantes

=== [ ] INC-01 — Escalada de privilegios en el registro público

[cols="1,3"]
|===
| Severidad | *ALTA*
| Archivo | `src/users/users.controller.ts:32`, `src/users/dto/create-user.dto.ts:31`
| Estado | Abierta
|===

`POST /users` quedó público con `@Public()`, pero `CreateUserDto` sigue aceptando
un `roleId` elegido por quien llama. `UsersService.create` solo comprueba que el
rol *exista y esté activo*; nunca que no sea un rol privilegiado.

Camino de ataque completo, sin autenticación en ningún paso:

. `GET /roles` — público desde `3ecccee`, devuelve `ADMIN` con su `id`
. `POST /users` con ese `roleId` — crea un administrador
. `POST /auth/login` — `AuthService` firma `role: user.role?.name` en el JWT

Está confirmado en la práctica: durante la sesión se crearon tres usuarios con rol
ADMIN sin enviar token (`ana.test.14181@mail.com`, `t3.8780@mail.com`,
`t4.*@mail.com`). No se usó ningún truco, es el comportamiento normal del endpoint.

*Cómo se arregla:* quitar `roleId` de `CreateUserDto` y que el servicio asigne
siempre un rol fijo no privilegiado. La asignación de roles debería vivir en un
endpoint aparte, protegido.

== Importantes

=== [ ] INC-02 — El guard de ADMIN se movió de `create` a `findOne`

[cols="1,3"]
|===
| Severidad | *MEDIA*
| Archivo | `src/users/users.controller.ts:46`
| Commit | `53835a1`
| Estado | Abierta
|===

El commit que abre el registro también eliminó `@UseGuards(AuthGuard, RolesGuard)`
y `@Roles('ADMIN')` de `create` y los agregó sobre `@Get(':id')`. Ese movimiento no
tiene relación con el objetivo declarado del commit.

Verificado contra el repositorio: tanto `95d56a8` como `origin/develop` tienen esos
decoradores sobre `create`, con `findOne` sin ninguno.

Dos consecuencias:

. No protege nada. `RolesGuard.canActivate` devuelve `true` incondicionalmente y
  nadie lee la metadata `'roles'`, así que el decorador solo *aparenta* restringir
  `GET /users/:id`.
. Filtra el token en los logs. `RolesGuard` hace `console.log(request)` sobre la
  request cruda de Express. `headers.authorization` queda a profundidad 2, que es
  la que imprime `util.inspect` por defecto, así que cada lectura de perfil vuelca
  el bearer del usuario al log.

Además reaplica `AuthGuard` de forma redundante, porque ya está a nivel de clase.

*Nota de proceso:* el cambio entró porque se hizo `git add` del archivo completo sin
revisar el diff antes de commitear. Conviene revisar `git diff --staged` antes de
cada commit.

*Cómo se arregla:* decidir si `GET /users/:id` debe ser solo para ADMIN. Si sí,
primero hay que implementar `RolesGuard` de verdad. Si no, revertir el movimiento.
En cualquier caso, sacar el `console.log`.

=== [ ] INC-03 — Cualquiera que se registre puede leer el directorio completo

[cols="1,3"]
|===
| Severidad | *MEDIA*
| Archivo | `src/users/users.controller.ts:38`
| Estado | Abierta
|===

`GET /users` pide token válido, pero ninguna restricción por rol. Combinado con el
registro público, cualquier persona anónima puede crear una cuenta descartable,
loguearse y volcar el correo, nombre, `roleId` y fechas de todos los usuarios.

Antes de estos commits hacía falta una cuenta provista por alguien. Ahora la barrera
es una sola request sin autenticar.

*Cómo se arregla:* restringir `GET /users` por rol, lo que depende de tener
`RolesGuard` funcionando. Ver `INC-08`.

=== [ ] INC-04 — Los roles desactivados quedan invisibles y no se pueden reactivar

[cols="1,3"]
|===
| Severidad | *MEDIA*
| Archivo | `src/roles/roles.controller.ts:30`
| Estado | Abierta
|===

`findAll` perdió el parámetro `isActive` y ahora fija `findAll(true)`.
`PATCH /roles/:id/status` permite desactivar un rol, pero `GET /roles` es el único
listado: una vez desactivado, el rol desaparece y no queda forma de descubrir su `id`
para volver a activarlo. Hoy le pasa a `REVISOR` (`id: 5`).

Efecto secundario: `GET /roles?isActive=false` ya no falla ni filtra. El
`ValidationPipe` global aplica `whitelist` y `forbidNonWhitelisted` a los cuerpos
ligados a un DTO, no a query strings sueltas, así que un cliente administrativo que
pida roles inactivos recibe los activos en silencio, sin un 400 que lo avise.

*Cómo se arregla:* un endpoint aparte protegido, tipo `GET /roles/all`, que conserve
el filtro completo para quien esté autenticado.

== Menores

=== [ ] INC-05 — `auth.guard.spec.ts` no compila

[cols="1,3"]
|===
| Severidad | *BAJA*
| Archivo | `src/auth/auth.guard.spec.ts:5`
| Estado | Abierta
|===

`AuthGuard` pasó a recibir dos argumentos (`JwtService` y `Reflector`), pero el spec
sigue haciendo `new AuthGuard()`.

[source]
----
src/auth/auth.guard.spec.ts(5,12): error TS2554: Expected 2 arguments, but got 0.
----

Es el único error de tipos del repositorio. No es una regresión: en `main` el
constructor ya pedía un argumento obligatorio, así que la llamada era igual de
inválida. `npm run build` no lo ve porque `tsconfig.build.json` excluye los specs.

*Cómo se arregla:* usar `Test.createTestingModule` con mocks de `JwtService` y
`Reflector`, como hacen el resto de los specs que sí funcionan.

=== [ ] INC-06 — `User.isActive` es `varchar` pero está tipado como `boolean`

[cols="1,3"]
|===
| Severidad | *MEDIA*
| Archivo | `src/users/entities/user.entity.ts`, `src/auth/auth.service.ts:36`
|===

La columna se declara `{ type: 'varchar' }` aunque la propiedad sea `boolean`.
`AuthService.login` hace `if (!user.isActive)` para rechazar usuarios inactivos. Un
`"0"` de MySQL es una cadena no vacía, o sea *truthy*, así que un usuario inactivo
pasaría el chequeo y podría iniciar sesión.

Conviene confirmarlo con un caso real antes de tocar nada.

NOTE: `Role.isActive` sí es `{ type: 'boolean' }`, así que la validación nueva de
`INC-01` no sufre este problema. Se verificó durante la revisión.

=== [ ] INC-08 — `RolesGuard` no aplica ninguna restricción

[cols="1,3"]

| Severidad | *ALTA* (bloquea INC-02 e INC-03)
